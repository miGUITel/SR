### **10. Cliente DNS (Resolver)**

El **resolvedor del sistema** recibe las peticiones de las aplicaciones. Puede utilizar fuentes locales o consultar el DNS configurado. Se debe distinguir del **resolvedor recursivo**, que normalmente trabaja en un servidor DNS y obtiene respuestas para sus clientes.

#### **10.1. Funcionamiento del Resolver DNS**

Una aplicación, como un navegador, solicita resolver un nombre. Según el sistema y su configuración, pueden intervenir `hosts`, una caché local y consultas DNS.

Si necesita DNS, el cliente pregunta a un servidor configurado. Este puede responder con los datos de sus zonas, usar su caché o consultar otros servidores. Después, el cliente entrega el resultado a la aplicación.

El orden entre las fuentes locales no es universal. Algunas aplicaciones también mantienen su propia caché o utilizan DNS seguro con una configuración distinta de la del sistema.

Consulta: [hosts en Windows y Linux](./SR03_hosts.md) y [resolución del cliente y del servidor](./SR0303+.md).

#### **10.2. Tipos de Resolvers**

Conviene distinguir funciones, sin tratarlas como categorías excluyentes:

- **Resolvedor del cliente**: normalmente envía la petición al DNS configurado.
- **Resolvedor recursivo**: asume la búsqueda por el cliente. Puede seguir referencias mediante consultas iterativas o usar reenviadores.
- **Caché**: puede existir tanto en el cliente como en el servidor. No constituye un tercer tipo de consulta DNS.

En el recorrido habitual de Internet, el cliente pide recursión a su servidor y ese servidor sigue la jerarquía cuando lo necesita. No todas las aplicaciones ni todos los servidores actúan igual.

#### **10.3. Herramientas de Consulta DNS**

Estas herramientas consultan directamente a un servidor DNS. No comprueban por sí solas el archivo `hosts` ni la caché local del sistema. Si consultan a un DNS que es un intermediario local, este sí puede usar sus propios datos y cachés.

##### **10.3.1. nslookup**

Sintaxis de consulta:

```text
nslookup [-type=TIPO] nombre [servidor]
```

Los corchetes indican elementos opcionales, no se escriben al ejecutar el comando.

```text
nslookup www.google.com
nslookup -type=MX google.com
```

Sin indicar servidor se utiliza el predeterminado que seleccione la herramienta. Para consultar el DNS del laboratorio, añade al final su IP real.

**Lectura de la salida**:

- Al principio aparecen el servidor consultado y su dirección. Si su nombre sale como «Unknown» o «Desconocido», puede faltar la resolución inversa de su IP. Comprueba también la respuesta obtenida.
- Después aparecen el nombre y los datos de la respuesta. No confundas estas IP con la del servidor consultado.
- Una respuesta no autoritativa puede ser válida.
- `NXDOMAIN` significa que el nombre consultado no existe según la respuesta.
- Un tiempo de espera agotado significa que no llegó respuesta a tiempo.

Las IP y el formato de salida cambian según el servidor, el sistema y el momento de la consulta.

**Modo interactivo**:

```text
nslookup
set type=MX
google.com
exit
```

##### **10.3.2. dig (Domain Information Groper)**

Herramienta de ampliación opcional. La consulta `dig google.com MX` pide los registros MX. Consulta [sintaxis y ejemplos adicionales](./SR0310bis.md).

##### **10.3.3. host**

Herramienta de ampliación opcional para consultas sencillas. No debe confundirse con el archivo `hosts`. Consulta [ejemplos de uso](./SR0310bis.md).

#### **10.4. Caché DNS y TTL**

La caché del cliente y la del servidor son independientes. Cada registro puede conservarse durante el tiempo indicado por su TTL. Al cambiar los datos de una zona, una caché puede seguir utilizando la información anterior hasta que caduque. También existen respuestas negativas en caché.

En Windows:

```text
ipconfig /displaydns
ipconfig /flushdns
```

`/displaydns` muestra la caché del cliente, que puede incluir entradas de `hosts` y consultas de otras aplicaciones. `/flushdns` limpia las entradas dinámicas de esa caché. No garantiza una salida vacía después: las aplicaciones pueden generar nuevas consultas. No vacía la caché de un DNS remoto ni necesariamente la del navegador.

En un Linux que utilice **systemd-resolved**, `resolvectl statistics` ofrece estadísticas y `sudo resolvectl flush-caches` limpia su caché. No todos los Linux usan ese servicio ni tienen una caché local. No se debe reiniciar un servicio distinto por suposición.

La rapidez de una consulta, por sí sola, no demuestra qué caché se ha utilizado.

#### **10.5. Resolución de Problemas con el Resolver DNS**

1. Comprueba qué DNS tiene configurado el cliente y qué servidor consulta realmente la herramienta.
2. Separa la IP del DNS consultado de las IP obtenidas como respuesta.
3. Distingue un nombre inexistente, la falta de un tipo de registro y la ausencia de respuesta.
4. Si el resultado del sistema y el de `nslookup` difieren, revisa `hosts`, cachés, sufijos de búsqueda y configuración de la aplicación.
5. Comprueba por separado la conectividad. Si `ping` muestra la IP, el nombre se ha resuelto aunque no lleguen respuestas ICMP.

Abrir una web puede desencadenar resolución DNS. Puede reutilizar una caché o un DNS propio del navegador. No demuestra por sí solo que se haya consultado el servidor del laboratorio.

En el laboratorio, utiliza el DNS previsto por su diseño. Cambiarlo directamente por un DNS público puede impedir resolver las zonas internas.
